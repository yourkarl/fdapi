# API 安全边界文档审查

> 视角说明：前三份报告分别覆盖了协议设计、逐方法参数 bug、类体系架构（对标地图 SDK）。这次换成**安全视角**：不是找代码漏洞（这是文档项目，看不到后端实现），而是找"哪些方法接受的参数会跨越信任边界（执行代码、加载外部内容、跨进程通信、读写文件路径），而文档完全没有说明这个信任边界该怎么把关"。这类文档空白的实际后果是：二次开发者可能把不受信任的数据（用户输入、第三方接口返回值）直接传给这些参数，而不知道自己在做什么。
>
> 定位：这是**文档缺口**审查，不是渗透测试报告，目的是补充"调用此方法时数据来源必须可信"这类说明，帮下游开发者规避误用，不涉及具体绕过手法。

## 一、`executeJsInTickPage(code, fn)` —— 接受任意 JS 字符串并执行

`docs/api/quickstart/digital-twin-api.md` {#executeJsInTickPage}：参数表里 `code` 类型 `string`，说明只有四个字："JS代码"。整份文档没有一句话提到：这段代码在什么上下文执行、和外部 `code` 参数的可信来源有什么要求。同类的还有 `registerTick(code, fn)`（"注册每帧渲染时要执行的JS脚本"），也是接受裸字符串当代码执行，同样没有安全提示。

**风险场景**：如果业务代码把这个 `code` 参数拼接了任何外部输入（比如从后台配置、用户表单拼出一段脚本字符串），等于把任意代码执行能力开放给了那个输入源的提供方。

**建议**：两处都补一句"`code` 参数会被直接作为 JavaScript 执行，请勿拼接任何未经过滤的外部输入（用户表单、URL 参数、第三方接口返回值等），仅用于开发者自己编写的固定脚本"。

## 二、`CustomTag.add()` 的 `contentURL`/`popupURL` —— 直接加载外部网页

`docs/api/marker/custom-tag.md` {#add}：`contentURL`（"网页URL（本地地址或者网络地址）"）和 `popupURL`（"弹出窗口的网页地址"）都是被直接当网页加载渲染的 URL，文档只字未提协议限制（是否只允许本域/https）、是否有沙箱隔离。`Marker`/`Panorama`/`VideoProjection` 里类似的 `popupURL`/`imagePath`/`videoURL` 参数（均支持"本地路径或网络地址"）也是同样情况。

**风险场景**：这些 URL 如果来自业务数据（比如资产管理系统里存的"点击查看详情"链接、第三方巡检系统同步过来的图片/视频地址），一旦数据源被污染或用户可编辑，这些字段实际上是**开放的网页加载入口**。

**建议**：在这几个类的对应参数说明里加一句"该 URL 会被直接加载渲染，如果数据来自用户输入或第三方系统，请在业务侧做协议与来源校验（如仅允许 https 且限定域名白名单）"。

## 三、`FdExternal.execute(json)` —— 已核实作用域有限，但接口本身缺少说明

`docs/api/utils/fd-external.md` {#execute}：明确写了运行环境仅限"Explorer WebUI / Marker 弹窗 / JSTick 调试窗口"三种 CEF 承载页面，并有 `.valid()` 方法可以检测是否在合法环境——**这一点比前两条设计得更谨慎，环境边界收得比较紧，不算真正的开放风险面**。但 `.execute(json)` 参数说明只有"要执行的JSON字符串"一句，完全没列出这个 JSON 能调用哪些底层接口、有没有权限分级——对于"仅在受控环境暴露、但内部能力边界不透明"的桥接类方法，建议补一份"通过 execute 可调用的底层接口清单"，而不是让开发者自己试。

## 四、资源路径参数未说明是否做路径穱越校验

`CustomObject.add()` 的 `pakFilePath`/`assetPath`、`TileLayer.add()` 的 `fileName` 等一系列文件路径参数，文档只给了示例格式（`@path:xxx.pak`、`HostConfig.Path + '/assets/...'`），**没有一处说明如果传入 `../../` 这类穿越路径、或者绝对路径/网络路径会怎样**（是被拒绝、被规整化，还是原样透传给底层文件系统）。这批参数数量多、分布在几乎所有涉及模型/图层加载的类里，不建议每处都补充，但建议在 `docs/tutorials/data-model.md`（模型资产与 pak 管线）或 `resources.md` 里统一加一条说明："文件路径类参数的取值应限定在工程约定的资源目录内，不建议接受用户可控的任意路径字符串"。

## 五、商业授权门槛与"静默失败"叠加，形成误用陷阱

`docs/tutorials/auth.md` 列出 `Vehicle2`/`Train`/`Drone`/`TrafficSimulation`/`BattlefieldSimulation`/`FiniteElement2` 等十几个类需要单独付费授权，原文写明"未授权时调用这些接口，方法会**静默失败**或返回错误回调"。但翻查这些类各自的方法文档页（如 `vehicle-2.md`、`train.md`），**没有任何一处在方法说明里提示"此方法需要额外授权"**，只有 `auth.md` 一处集中声明。这不算传统意义的安全漏洞，但和此前"错误码孤岛"问题同源：开发者按单个类文档集成，代码测试期一切正常（用测试授权账号），上线后如果授权模块没跟着买，方法调用悄悄失效却难以定位原因。

**建议**：把 `auth.md` 里列出的这些类，在各自文档页顶部加一条"⚠ 本对象需要额外授权模块（见[高级接口授权](/docs/tutorials/auth)）"的提示，而不是只在一个独立页面声明。

## 优先级建议

| 优先级 | 条目 | 说明 |
|---|---|---|
| 高 | 一（executeJsInTickPage/registerTick 补充安全提示） | 影响面明确，改动量小 |
| 高 | 五（授权类文档页补提示） | 与已发现的"错误码孤岛"问题同源，一次性处理 |
| 中 | 二（外部URL加载参数补充协议/来源提示） | 涉及多个类，建议先统一措辞再批量应用 |
| 低 | 三（FdExternal.execute 补充可调用接口清单） | 需要向工程侧要清单，非纯文档工作 |
| 低（集中说明即可） | 四（路径参数统一在概念页说明，不逐处修改） | 参照 pak 管线教程已有模式 |
