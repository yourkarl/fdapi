## 一、P0｜派生文件可能与源文档静默不一致（CI 无校验）

**问题**：`docs/api/*.md` 是手写源，`static/dts-sdk.d.ts`、`src/data/{api-completions,param-meta,real-examples}.js`、`static/llms*.txt` 全部是 `npm run gen` 的派生物。但 CI（`.github/workflows/build.yml`）只做：语法检查 → 完整性检查 → `npm ci` → `npm run build`，**没有任何一步校验「派生物是否与当前源文档一致」**。

后果：贡献者改了 `docs/api/*.md` 却忘了跑 `npm run gen` 就 push，构建照样通过、站点照样上线，但 IDE 类型提示 / 调试台补全 / 参数面板全部落后于文档——且**没有任何报错**。这正是 07-09 那次 `gen_dts.py` 事故的同类型风险，只是这次不会以「d.ts 变成空壳」这种显眼方式暴露。

**证据**：`check_docs_integrity.py` 只把 `dts-sdk.d.ts` 当作"要检查 UTF-8/无 NUL 的文件"（第 74 行），不比对内容。

**建议**：CI 增加一步「重新生成 + `git diff --exit-code`」：

```yaml
- name: Verify generated artifacts are up to date
  run: |
    python3 gen_dts.py && python3 gen_param_meta.py && \
    python3 gen_real_examples.py && python3 gen_llms_txt.py
    git diff --exit-code || (echo "派生物与源文档不一致，请本地运行 npm run gen 后提交" && exit 1)
```

注意 `gen_real_examples.py` 依赖 `参考资料/` 目录，需确认 CI checkout 后该目录存在（当前已被 git 跟踪，应该没问题）。

## 二、P0｜`d.ts` 类型声明缺 `fdplayer` 与 `FdExternal`，与文档承诺不符

**问题**：`static/dts-sdk.d.ts` 只有 **1 个** `declare namespace fdapi`，共 1334 方法。但文档里有两大块完全不在其中：

- **`DigitalTwinPlayer`**：15 个方法（`getAPI`、`getHost`、`resize`、`getVideoElement`、`getInstanceInfo`、`setInstanceOptions`、`setResolution`、`setKeyEventTarget`、`setEnableEventSync`、`setActionEventEnabled`、`getVideoElementSize`、`getVideoStreamSize`、`getVideoSize` 等）——全都检索不到。
- **`FdExternal`**：7 个方法（`execute`、`getData`、`setData`、`postEvent`、`getViewportSize`、`valid`、`close`）——同样缺失。

而 `SKILL.md` 的初始化模板明确写 `const player = new DigitalTwinPlayer(host, options)`，readme 也宣传「TS 类型声明 + IDE 智能提示」。结果就是：**用户按文档写 `new DigitalTwinPlayer(...)` 时，IDE 直接报红「找不到名称」**——这和「提供 IDE 智能提示」的承诺相反。

**复现**：`grep -c "DigitalTwinPlayer" static/dts-sdk.d.ts` → 1（仅出现在注释里）；`grep -c "declare namespace" static/dts-sdk.d.ts` → 1。

**根因**：`gen_dts.py` 只解析 `docs/api/**` 中带 `### 方法()` 锚点的类文档，而 `DigitalTwinPlayer` 是构造函数式类（方法标题格式不同）、`FdExternal` 是静态类，都没被收进去。

**建议**：二选一——
1. 扩展 `gen_dts.py`：补一个 `declare class fdplayer`（含构造函数签名与 15 个方法）+ `declare namespace fdapi.fdExternal`；或
2. 手写一个 `static/dts-extras.d.ts` 并在构建时拼接到 `dts-sdk.d.ts` 头部，避免被 `gen` 覆盖。

同时把 `dts-sdk.d.ts` 的「已覆盖/未覆盖类」清单写进 readme，避免用户误以为它是全量声明。

## 三、P1｜新一轮同步的**索引遗漏**（本次改动的直接遗留）

以下都是本轮新增 3 类 / 58 方法时没同步到的位置，属于「加了内容但没登记」型疏漏：

1. **`types.md` 未收录新增枚举 `RockStyle`**：`rockburst.md` 里 `style` 参数的说明写「详情参考 `RockStyle`」，但 `grep -c RockStyle docs/api/types.md` → **0**。用户点不到任何解释，属于典型的"悬空类型引用"。Rockburst 还引用了 `booleanOperations` 等结构，也应一并登记。

2. **`BaseObject` 未被任何子类文档反向引用**：新建的 `base-object.md` 只有它自己（和 viewshed/rockburst）链到，而真正该链它的 60+ 个子类文档（Marker、Polygon、Fluid……）里，`updateBegin/updateEnd` 仍是各自展开的重复说明。`grep -rl "base-object" docs/api/` → **2**。既然已经建了基类页，就该让子类指过去，否则这个页只是又多了一处重复。

3. **新页面交叉引用密度偏低**：`viewshed.md` 与 `rockburst.md` 各只有 **1** 条 `/docs/api/` 内链，而 `marker.md` 有 12 条。可视域至少应链到 `globe-terrain`（地形影响可见性判断）、`tools.startViewshedAnalysis`（对比用法）、`camera`（focus 联动）；岩爆应链到 `model`（模型加载）与 `settings`。

4. **`readme.md` 的数量描述已过期**：写「API 文档（100 篇）、教程（18 篇）」，实际 **API 86 篇 / 教程 51 篇**。教程数差近 3 倍，会让新贡献者低估站点的内容规模。

## 四、P1｜「伪示例」仍有 101 处

**问题**：`grep -rn "具体数据结构见示例\|详见示例\|见下方示例" docs/api/*/*.md | wc -l` → **101**。

这是《API文档工程隐患评审》第 11 条点过的老问题（当时举例 `River.get()` / `Satellite.get()`），当时只修了举到的几个，其余批次没清完。文档说"返回值见示例"，但示例块里只有调用语句、没有返回 JSON——**文档承诺与实际内容不符**，比直接不写更误导。

**建议**：把 101 处按「有真实返回数据可补 / 只能保留说明」二分。前者补齐（可从 `参考资料/doc/scripts/api_examples*.js` 与 `ac.min.js` 的返回结构反推），后者改成统一的「本方法返回结构与 `Xxx.get()` 一致，见该页示例」这类明确指向，不再用"见示例"这种无指向措辞。

## 五、P2｜工程卫生（不影响正确性，影响长期可维护性）

1. **根目录混入 3 个与文档站无关的脚本**：`gen_brief_pdf.py`（其他事项速查）、`gen_phrases_pdf.py`（阿布扎比出差英语 50 句）、`merge_notes_pdf.py`（出差注意事项 PDF 合并）。它们与 `npm run gen` 管线的文件名风格（`gen_*`）高度相似，极易被误认为管线的一部分并被 CI 的语法检查扫到。建议移到 `tools/personal/` 或直接移出仓库。

2. **根目录 12 份 .md 报告与站点内容混放**：9 份评审报告 + readme + 本报告。它们不该参与站点构建（当前没进 `docs/`，安全），但堆在根目录会让「这是文档工程还是评审归档」界限模糊。建议归入 `reports/`。

3. **CI 语法检查清单仍含两个已封存脚本**：`regenerate_docs.py`、`gen_sidebar.py`（build.yml 第 31 行）。07-08 报告已建议移除，至今未动。无害，但与 readme「已封存」的措辞不一致。

4. **仓库体积仍在膨胀**：`.git` **328MB**、`static/img/refdoc` **320MB**（单个 GIF 最大 10.9MB）、`参考资料` **437MB**。前三轮报告都提过但未处理。`参考资料/` 本质是构建输入而非产物，是最大的一块——可考虑移出仓库（仅保留 `doc/doc/*.html` 与 `doc/scripts/api_examples*.js` 这两个真正被脚本读取的子集，其余 images/ 300MB 删掉）。

5. **`.claude/settings.local.json` 残留旧机器绝对路径**：大量 `D:\工作备份\DTS文档改版\docusaurus\` 的 allow 规则，工程已迁到 `F:\DTS-Skill\fdapi`，这些规则全部失效。

## 六、P2｜能力层面仍未落地的两项（前轮已规划，未见进展）

1. **多版本文档**：仍无 `versions.json`。SDK 已到 v7.1，而 `readme` 与站点标题都只对应单版本。当 7.2 发布时，`updateBegin` 之外的 API 变更（如本轮 4 个废弃方法）会让老项目用户失去对应版本的文档。启用 Docusaurus versioning 的成本很低，建议在 7.2 发布前做。

2. **示例中心独立页**：`src/pages/` 下是 `index / instance-manager / sandbox / spatial-tools`，没有示例中心。`real-examples.js` 已有 1741 条真实示例（投影 1069 + 球面 672），数据是完全现成的，缺的只是一个可按场景浏览/搜索的页面。这是投入产出比最高的一项。

## 结论

前四轮报告的核心判断（「返回值缺失是最大短板」「错误码是孤岛」）在当前版本**已经不成立**——这两项分别修到 3% 和 90% 引用率，示例覆盖 94%，文档内容本身没有明显硬伤。

当前真正值得投入的是两件事：**让 CI 守住派生链路**（否则改动会静默失配），**让类型声明与文档承诺对齐**（否则 IDE 体验与宣传相反）。这两项都不大，但属于「不做就会持续积累隐性技术债」的类型。

其余为整理性工作，可按需推进。
